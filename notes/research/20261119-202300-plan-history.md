## Bottom line

1. **The team fixes the funnel one gate at a time, on single runs.** About 40 plans react to the latest single run of one of the three private eval cases (all from one repository). A found bug dies at some gate between Stage 7 and publication. The plan patches that gate, and the next run loses it at the next gate. Examples: 12→23→24→30; 72→73→74; 106→107→108→109→110 (all from private case A runs 52–57); 63→64→65→66. The root problem is structural: a long publication path where every gate can silently drop a finding. Adding rescue lanes treats symptoms.
2. **Recall mechanisms accumulate and none retire.** Promotion (81, `uncertainty-promotion.ts` 1,039 lines), the K>1 ensemble (84), the adaptive second pass (92) and coverage escalation E1 (92) all target the same Stage-7 variance. All four are still in code. Plan 81's promised ≥500-line deletion never happened (the file grew from 859 to 1,039 lines). Plan 92 said the adaptive pass "subsumes the promotion lane's rationale", and that never paid off. The ensemble sunset clock has stood at 18/20 since July (PUNCHLIST:71).
3. **The evals measure a different product from the one users get. Verified (me).** `review.adaptiveSecondPass` defaults to off (`src/pipeline/lens-runner.ts:230,271`; PUNCHLIST:126 says "KEEP, eval-enabled, no product default"). Two of the three private eval case configs turn it on (aggregate count from the private evals repo; read with owner approval). The CLI and Action ship without it, so eval recall overstates production recall by an unmeasured amount. **Decision needed:** enable it by default or remove it from the eval configs.
4. **Structured-output repair keeps growing back.**
   - Fable's review called it "interest payments on schema surface" (RV1 §2.3). Plan 95 consolidated the seam, and then 111, 112, 114, 115, 116, 120 and 124 each added a layer.
   - `pi-runner.ts` grew from 3,527 to 4,429 lines. `RUNNER_MESSAGE_VERSION` is at v24.
   - Plan 95's census already found only 10 schema-invalid calls out of 2,436, after plan 86 step 3 removed most of the friction.
   - The 0.6.0 squash `8695486` reversed three hard plan invariants without amending the plans:
     - "exactly one model repair" became `MAX_SCHEMA_REPAIR_ATTEMPTS = 3` (`src/llm/pi-runner.ts:181`, verified (me));
     - "never resend rejected arguments" became 512-char excerpts and 16 KB samples;
     - "no field-edit tool" became `field-repair.ts`.
5. **The measurement culture of July decayed after August.**
   - From plan 111 on, plans land with unit-test validation only. More than 12 plans end in "live validation pending" (README:126–130).
   - The `repeat:10` runs that plans 76, 81 and 84 asked for never ran.
   - Gates written into plans were bypassed in squash merges: 101's paid A/B, 39 and 43's "measure first", and the step-down default flipped in 0.6.1 (`src/config/schema.ts:209`) despite 117, 118 and 120 each saying "do not change reasoning without a controlled comparison".
   - Scorer artifacts were mistaken for regressions three times (plans 16/41; `minFindings:1` passes before run 31; opus-vocabulary `titlePattern`s in RV3). Even so, scorer decision D8 from RV1 is still open.
6. **Cost cuts that strip context or transcripts lose recall, and were reverted every time.** 33 (compact finalize) was turned off by 40 and deleted by 43. 20 (fuzzy clustering) was replaced by 87. 36 plus the "no finding is success" framing was undone by 44. 51/52 compact repair was undone when the composer went back to full-context repair. 102 (packing) cut cost 1.4% and time 6.1% end to end, failed its gate and was torn down. Any fast lane that shrinks the Stage-7 transcript or adds silence-biased framing repeats this history.
7. **The records disagree with each other and with the code.**
   - README statuses are stale in both directions (14 rows), and 106–110 still say PENDING in their own headers.
   - PUNCHLIST stopped on 2026-07-24 and misses plans 100–125.
   - `specs/reviews/` is git-ignored, so decisions in tracked plans cite evidence nobody can retrieve from Git.
   - The project spec still says "one repair" (architecture.md:1217; review_pipeline.md:544,625,678,788).
   - That is four ledgers for one fact, against the owner's "no dual sources of truth".

## Code bugs and hazards found while verifying

**Verified by reading (me):**
1. **Telemetry nesting.** `human-attention.ts:283–302`: the `human_attention_hints_suppressed_by_adjudicated_reject` event sits inside `if (suppressedByFindings.length > 0)`, so it is lost whenever no note was also suppressed by a finding. No test asserts it. Severity low; telemetry only.
2. **Run-fatal by default.**
   - `isRunFatalLlmError` is "LLM failure and `recoverable !== true`" (`pipeline-utils.ts:5–7`), and `CodegenieError` defaults `recoverable` to false (`util/errors.ts:36`). Every new throw site is therefore run-fatal unless marked otherwise. This is the reverse of plan 80's intent.
   - Concrete sites: the composition primary-call allowance throws `llm_call_failed` without `recoverable` (`pi-runner.ts:1283–1284`). `canUseComposerFallback` then rejects it (`composer.ts:796–798`), and the composer rethrows (`composer.ts:127–136`), dropping verified findings. That is the run-16 shape plan 80 fixed. Separately, the recovery inventory overflow throws `llm_schema_invalid` with `recoverable: false` (`pi-runner.ts:312–314,712–714`); Stage 9 rethrows it with no schema-invalid exemption (`verifier.ts:371` versus Stage 7's exemption at `lens-runner.ts:139`).
   - Reachability of both sites in real runs is not verified. Severity: medium to high when reached.
3. **Eval/product configuration split** on `adaptiveSecondPass` (bottom line 3). Decision needed.

**Hypotheses from the batch audits (worth a cheap check):**
- **Over-broad cache fingerprint.** It hashes the absolute `repoRoot` plus concurrency, timeouts and similar settings (`review-runner.ts:844–869`). Fixture evals run from `<runDir>/fixture-repo` (`eval-runner.ts:994`), so no model-call cache is reused across eval runs. This contradicts plan 35 step 5. It is a candidate cause for **GitHub #30** ("model-call cache barely replays").
- **Raw arguments in telemetry.** `field_repair_rejected` records Pi's validation message without stripping the "Received arguments:" suffix (`pi-runner.ts:678–681`). Other sites do strip it (`:2212`, `stage7-submit-repair.ts:193`).
- **Attention errors trigger whole-report fallback.** Attention-decision errors are `schema_invalid` (`composer.ts:428–429`), so bookkeeping errors can push the whole report into fallback. Plan 121 forbade this; 8cbe1ce reversed it.
- **False "planner failed" banner.** Recovered plans that are deliberately sparse get forced to deep coverage and a false banner (`planner.ts:334,367,558–566`, `coverage-summary.ts:16–21`).
- **Revise misclassified.** `verifier.ts:1110–1116` labels a failing `revise` that carries only `findingUpdates` as having no payload.
- **Go test files not recognised.** `isCompositionTestPath` misses `*_test.go` (`path-roles.ts:13–18`, pinned by a test), while the other test-path dialects match it.
- **"token" means security.** The promotion security regex matches `token` (`uncertainty-promotion.ts:758`), which in token-heavy financial code routes hints to security/high severity.
- **Unbounded escalation.** E1 coverage escalation has no packet bound (`coverage-escalation.ts:22–45`), although plan 92's own stop condition required one.
- **Over-failing health.** `review-health.ts:52–59` marks health failed on any unclassified tool error when the packet emitted any hint, and the CLI then exits 1.
- **Wider default author list (decision).** The Action's default `allowed-associations` includes `CONTRIBUTOR`/`FIRST_TIME_CONTRIBUTOR` (`event-gate.ts:13–19`), against plan 97 §2. A live write-permission check mitigates it (`issue-comments.ts:110`).
- **Low-confidence inline comments (decision).** The low-confidence hatch `publish` bypasses `minInlineConfidence` (`composer.ts:1633–1660`).

## Lessons the team keeps relearning

1. **"Single runs decide nothing."** Stated in RV1 L20, RV2 L92, RV3 L28 and plans 56, 65, 66, 72, 76 and 79. Each time the next plan is still triggered by, and judged on, one to three runs. Every past attempt to fix this added harness machinery (`repeat`, `minRecallRate`) that nobody then configured. What is missing is a pre-registered N per decision and someone who owns the measurement round.
2. **"Generate liberally, verify strictly."** (44, re-applied in 81, 84 and 92.) It holds whenever followed. Every violation (33, 36) was reverted.
3. **"Deterministic fixes stick; posture and heuristic fixes get reverted."** (RV1 L150.) Confirmed: all Wave-1/2 deterministic fixes are still at master, and the heuristic layers are the churn.
4. **"Do not let the planner drive control flow."** (66.) It was relearned after 60 and 63–65. 67 then added planner fields that 71 had to trim because the heavier prompt broke first-submit validity.
5. **"Define the decision rule, don't add code."** The two cross-model defects that were actually fixed were fixed by defining enum semantics in one prompt sentence: `reviewStatus:"incomplete"` (RV3 L21–22) and candidate-versus-hint (RV1 L186). Undefined contract semantics are "a per-model lottery". This is the cheapest multi-model hardening lever.
6. **Measurement gates get bypassed by squash merges and same-day landings** (39, 43, 98–101 in one squash, 0.6.0 and 0.6.1). Each plan's STOP conditions are qualitative; only plan 71 defines a measurable rate.
7. **Thresholds follow incidents.** The ensemble cap of 8 and adaptive cap of 4 were both added after one run (private case B, run 52). `maxBudgetTokens` went 6M→7M→8M in days. The 3 / 0.24 association thresholds are duplicated as literals in two modules (`uncertainty-promotion.ts:388`, `human-attention.ts:684`). `budgetBoost` also silently scales verification admission lanes (`verifier.ts:1449`, `uncertainty-promotion.ts:993`). None of these is a user knob, which follows the letter of "no new tunable thresholds", but together they amount to roughly 100 unlabelled policy constants with no recorded calibration.

## What the history implies for the synthesis

Each item is a recommendation with its measurement.
- **Simplify by deletion first.** Remove the verified-dead residue: one PR, zero behaviour change. Measure with green `pnpm check`/`pnpm test` and the LOC delta.
- **Close the open decisions before building anything new:**
  - adaptive pass: product default or eval-off;
  - ensemble K>1: delete when the 20-run clock completes, or now by owner call;
  - 113 and 112's corpus gate: retire, or measure from the existing `finalArgumentStates`;
  - RV1 D8 scorer leniency;
  - PR #40 / RV4.
  - Kill criterion: any mechanism with no recorded rescue in the retained runs is deleted.
- **Shorten the publication funnel instead of adding rescue lanes.** Use the existing loss-stage labels (`eval-scoring.ts:205` `attributeLoss`) over every retained run to count losses and rescues per gate. Delete gates with zero rescues, and merge gates that duplicate one decision (confidence cliff, anchor withholding, note suppression).
- **Restore plan 80's polarity:** LLM errors are stage-local unless positively auth or provider-wide. Measure with an injected-error test at each throw site.
- **One ledger.** The plan header status is the single source of truth. Generate the README from the headers or delete it, archive PUNCHLIST, and move the evidence that `specs/reviews` holds into tracked notes, or say explicitly that it is private.
- **Measurement protocol for every later plan.** Pre-registered N per arm, at least one case outside the single private eval repository, first misses adjudicated by hand, and a controlled baseline frozen before the next change stacks on top.
- **Correction from @architect-2.** "All real-model evidence comes from one repository" is true for the *controlled* eval suite: 3 cases, all from one repository; the private eval suite was last updated 2026-09-24. Uncontrolled real-model reviews do exist elsewhere: the reviews recorded in plan 124 L3–31, and subscription-backed eval 129 in plan 123 L191.
